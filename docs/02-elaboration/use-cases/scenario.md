CCILS의 UC-01: OIDC 기반 통합 로그인 및 토큰 발급을 기준으로 성공 시나리오를 선정하면 다음 5가지가 적절합니다.

Collaboration Model과 Sequence Diagram으로 확장할 것을 고려해, 각 시나리오의 사전 조건(Precondition), 실행 흐름(Main Flow), 사후 조건(Postcondition) 을 구분하겠습니다.

## 1. 성공 시나리오 후보

| ID | 성공 시나리오                                 | 핵심 검증 대상                           |
| -- | --------------------------------------- | ---------------------------------- |
| S1 | 최초 로그인 및 토큰 발급 성공                       | OIDC 인증, Authorization Code, 토큰 발급 |
| S2 | 기존 SSO 세션을 이용한 로그인 성공                   | 세션 재사용, 재인증 생략                     |
| S3 | 정상적인 서비스 접근 권한을 가진 사용자 로그인 성공           | 중앙 서비스 접근 자격 검증                    |
| S4 | 다른 연동 애플리케이션으로 SSO 로그인 성공               | 다중 클라이언트 지원                        |
| S5 | Authorization Code + PKCE 검증 후 토큰 발급 성공 | Code 및 PKCE 검증, 토큰 교환              |

S1이 기본 성공 시나리오이고, 나머지는 특정 기능이나 조건을 강조하는 성공 시나리오입니다. S1과 S3·S5는 일부 처리 단계가 중복됩니다.

## 2. 시나리오별 상세 흐름

### S1. 최초 통합 로그인 및 토큰 발급 성공

대표 성공 시나리오

사전 조건: 사용자는 CCILS에 등록된 활성 계정과 올바른 인증 정보를 가지고 있으며, 연동 애플리케이션은 CCILS에 등록되어 있습니다.

1. 사용자가 LMS에 접속해 로그인을 요청합니다.
2. LMS가 사용자를 CCILS의 OIDC 인증 엔드포인트로 이동시킵니다.
3. CCILS가 클라이언트 정보와 인증 요청을 검증합니다.
4. 사용자가 아이디와 비밀번호를 입력합니다.
5. CCILS가 사용자 인증과 계정 활성 상태를 확인합니다.
6. CCILS가 LMS 접근 자격을 확인하고 중앙 인증 세션을 생성합니다.
7. CCILS가 Authorization Code를 발급합니다.
8. LMS가 Authorization Code와 PKCE 검증값을 이용해 토큰을 요청합니다.
9. CCILS가 요청을 검증하고 ID Token 및 Access Token을 발급합니다. Refresh Token은 허용된 정책에 따라 발급합니다.
10. LMS가 ID Token을 검증하고 로그인 세션을 생성합니다.

사후 조건: 사용자는 LMS에 로그인된 상태가 되며, CCILS에는 유효한 중앙 SSO 세션이 존재합니다.

### S2. 기존 SSO 세션을 이용한 로그인 성공

사전 조건: 사용자는 이미 CCILS에 로그인하여 유효한 SSO 세션을 가지고 있습니다.

1. 사용자가 학사 관리 시스템에 접근합니다.
2. 학사 관리 시스템이 CCILS에 OIDC 인증을 요청합니다.
3. CCILS가 기존 SSO 세션의 유효성을 확인합니다.
4. 사용자에게 비밀번호를 다시 요구하지 않고, 계정과 서비스 접근 자격을 확인합니다.
5. CCILS가 새로운 Authorization Code를 발급합니다.
6. 학사 관리 시스템이 Code를 교환해 토큰을 획득하고 검증합니다.

사후 조건: 사용자는 별도의 비밀번호 입력 없이 학사 관리 시스템에 로그인합니다.

### S3. 서비스 접근 자격 확인 후 로그인 성공

사전 조건: 사용자에게 `LMS_ACCESS` 접근 자격이 부여되어 있습니다.

1. 사용자가 LMS 로그인을 요청합니다.
2. CCILS가 사용자를 인증합니다.
3. CCILS가 사용자와 LMS의 서비스 접근 자격 관계를 조회합니다.
4. `LMS_ACCESS = ALLOWED` 상태를 확인합니다.
5. CCILS가 인증 절차를 완료하고 Authorization Code를 발급합니다.
6. LMS가 Code를 토큰으로 교환한 뒤 인증 결과를 검증합니다.

사후 조건: LMS 접근 자격을 가진 사용자만 정상적으로 로그인할 수 있습니다.

### S4. 여러 애플리케이션 간 SSO 로그인 성공

사전 조건: 사용자는 CCILS에서 인증을 완료했으며 LMS와 도서관 시스템 모두에 접근 자격이 있습니다.

1. 사용자가 LMS에서 로그인합니다.
2. CCILS가 중앙 SSO 세션을 생성합니다.
3. 사용자가 도서관 시스템으로 이동합니다.
4. 도서관 시스템이 CCILS에 OIDC 인증을 요청합니다.
5. CCILS가 기존 SSO 세션을 재사용합니다.
6. 도서관 시스템용 Authorization Code 및 토큰 발급 과정을 완료합니다.
7. 도서관 시스템이 토큰을 검증합니다.

사후 조건: 사용자는 두 개의 애플리케이션에 로그인한 상태이며, CCILS의 중앙 SSO 세션을 공유합니다. 각 애플리케이션은 자체 로그인 세션을 유지할 수 있습니다.

### S5. Authorization Code와 PKCE 검증 후 토큰 발급 성공

사전 조건: 유효한 Authorization Code가 발급되었으며 클라이언트가 해당 요청의 `code_verifier`를 보유하고 있습니다.

1. 연동 애플리케이션이 Authorization Code를 CCILS의 Token Endpoint에 제출합니다.
2. CCILS가 클라이언트 인증 또는 식별, Redirect URI, Code 유효성을 해당 클라이언트 유형과 프로토콜 규칙에 따라 검증합니다.
3. CCILS가 `code_verifier`와 기존 `code_challenge`의 일치 여부를 확인합니다.
4. CCILS가 Authorization Code를 일회용으로 소비 처리합니다.
5. CCILS가 ID Token과 Access Token을 생성하고 서명합니다.
6. CCILS가 토큰 응답을 반환합니다.
7. 클라이언트가 ID Token을 검증합니다.

사후 조건: 클라이언트가 유효한 토큰을 획득했으며, 동일한 Authorization Code는 다시 사용할 수 없습니다.
