# CILS 기능 요구사항 명세서 (Functional Requirements)

| 항목 | 내용 |
|---|---|
| 프로젝트 | CILS (중앙 통합 로그인 시스템) |
| 문서 ID | CILS-SRS-FR |
| 문서 버전 | v0.1 (Draft) |
| 문서 상태 | 초안 |
| 개발 방법론 | Lightweight RUP |
| 관련 산출물 | UC-01, UC-02, UC-03, ADR-001 |

## 1. 개요

### 1.1 문서 목적

본 문서는 CILS가 제공해야 하는 기능적 요구사항을 정의한다.

CILS는 대학 내 여러 애플리케이션의 사용자 인증을 중앙에서 수행하며, OIDC 기반 SSO(Single Sign-On)와 RBAC(Role-Based Access Control)를 이용한 애플리케이션 접근 인가를 제공한다.

본 문서에 정의된 요구사항은 시스템 설계, 구현, 테스트 및 요구사항 추적 관리의 기준으로 활용한다.

### 1.2 시스템 범위

CILS가 담당하는 주요 기능은 다음과 같다.

- 사용자 계정 인증
- OIDC 기반 인증 요청 처리 및 토큰 발급
- 중앙 SSO 세션 관리
- 로그아웃 및 인증 상태 무효화
- Role 기반 애플리케이션 접근 인가
- 연동 애플리케이션 등록 정보 관리

### 1.3 범위 밖 
**CILS는 연동 애플리케이션에 대한 접근 가능 여부만 판단한다.** 애플리케이션 내부 기능 및 데이터에 대한 세부 접근 권한은 각 애플리케이션이 독립적으로 관리한다.

## 2. 사용자 및 연동 애플리케이션

### 2.1 사용자 역할

| Role | 설명 |
|---|---|
| `STUDENT` | 학생 |
| `PROFESSOR` | 교수 |
| `STAFF` | 교직원 |
| `ADMIN` | 관리자 |

### 2.2 연동 애플리케이션

| 애플리케이션 | 서비스 코드 |
|---|---|
| 학생포털 | `STUDENT_PORTAL` |
| 교수포털 | `PROFESSOR_PORTAL` |
| 교직원포털 | `STAFF_PORTAL` |

### 2.3 Role별 애플리케이션 접근 정책

| 애플리케이션 | STUDENT | PROFESSOR | STAFF | ADMIN |
|---|:---:|:---:|:---:|:---:|
| 학생포털 | O | X | X | O |
| 교수포털 | X | O | X | O |
| 교직원포털 | X | X | O | O |

※ O: 접근 허용 / X: 접근 거부

본 접근 정책은 ADR-001에 따라 정의한다.

## 3. 기능 요구사항

### 3.1 사용자 인증 (Authentication)

#### FR-001. 사용자 ID/PW 인증

**설명**

CILS는 사용자 ID와 비밀번호를 이용한 인증 기능을 제공해야 한다.

**상세 요구사항**

- FR-001-01: CILS는 사용자에게 로그인 화면을 제공해야 한다.
- FR-001-02: CILS는 입력된 사용자 ID에 해당하는 계정을 조회해야 한다.
- FR-001-03: CILS는 입력된 비밀번호를 해싱해서 단방향 저장해야한다.
- FR-001-05: 인증에 실패하면 로그인 요청을 거부해야 한다.
- FR-001-06: 인증에 성공하면 중앙 로그인 세션을 생성할 수 있어야 한다.

**검증 기준**

- 올바른 계정 정보로 인증에 성공한다.
- 잘못된 비밀번호로 인증에 실패한다.

**관련 Use Case:** UC-01

#### FR-002. 기존 인증 상태 확인

**설명**

CILS는 사용자의 기존 중앙 SSO 세션을 확인하고, 유효한 인증 상태를 재사용할 수 있어야 한다.

**상세 요구사항**

- FR-002-01: CILS는 브라우저의 중앙 세션 쿠키를 통해 기존 인증 상태를 확인해야 한다.
- FR-002-02: 유효한 SSO 세션이 존재하면 사용자 ID/PW 입력을 생략할 수 있어야 한다.
- FR-002-03: 유효한 세션이 없거나 만료된 경우 사용자 재인증을 요구해야 한다.
- FR-002-04: 기존 세션을 재사용하는 경우에도 요청한 애플리케이션에 대한 접근 인가를 수행해야 한다.

**검증 기준**

- 기존 SSO 세션이 유효하면 재로그인 없이 인증 절차가 진행된다.
- 만료된 SSO 세션은 재인증을 요구한다.

**관련 Use Case:** UC-01

### 3.2 OIDC 인증 및 토큰 발급

#### FR-003. OIDC 인증 요청 검증

**설명**

CILS는 연동 애플리케이션의 OIDC 인증 요청을 검증해야 한다.

**상세 요구사항**

- FR-003-01: 등록된 `client_id`인지 확인해야 한다.
- FR-003-02: 요청한 `redirect_uri`가 클라이언트 등록 정보와 일치하는지 검증해야 한다.
- FR-003-03: 클라이언트에 허용된 인증 방식과 Scope를 검증해야 한다.
- FR-003-04: PKCE 관련 요청 파라미터를 검증해야 한다.
- FR-003-05: 유효하지 않은 인증 요청은 거부해야 한다.

**검증 기준**

- 등록된 클라이언트의 유효한 인증 요청은 처리된다.
- 등록되지 않은 Client ID 또는 Redirect URI를 사용하는 요청은 거부된다.

**관련 Use Case:** UC-01

#### FR-004. Authorization Code 발급

**설명**

CILS는 사용자 인증 및 애플리케이션 접근 인가에 성공한 요청에 대해 Authorization Code를 발급해야 한다.

**상세 요구사항**

- FR-004-01: 사용자 인증 상태가 유효한지 확인해야 한다.
- FR-004-02: 요청한 애플리케이션에 대한 Role 기반 접근 인가가 성공해야 한다.
- FR-004-03: 인증 및 인가 조건을 만족한 경우 일회용 Authorization Code를 발급해야 한다.
- FR-004-04: Authorization Code를 요청한 클라이언트 및 인증 요청 정보와 연결하여 관리해야 한다.
- FR-004-05: Authorization Code에는 유효기간을 적용해야 한다.
- FR-004-06: 접근 인가가 거부된 경우 Authorization Code를 발급하지 않아야 한다.

**검증 기준**

- 접근이 허용된 사용자는 Authorization Code를 발급받을 수 있다.
- 접근이 거부된 사용자는 Authorization Code를 발급받지 못한다.
- 만료된 Authorization Code는 사용할 수 없다.

**관련 Use Case:** UC-01

#### FR-005. Authorization Code 교환

**설명**

CILS는 유효한 Authorization Code를 토큰으로 교환하는 기능을 제공해야 한다.

**상세 요구사항**

- FR-005-01: CILS는 Token Endpoint를 제공해야 한다.
- FR-005-02: 클라이언트 인증이 요구되는 경우 해당 클라이언트를 인증해야 한다.
- FR-005-03: Authorization Code의 유효기간과 사용 여부를 확인해야 한다.
- FR-005-04: Authorization Code가 요청한 클라이언트에 연결되어 있는지 확인해야 한다.
- FR-005-05: PKCE `code_verifier`를 검증해야 한다.
- FR-005-06: 정상적으로 교환된 Authorization Code는 재사용할 수 없어야 한다.
- FR-005-07: 검증에 실패하면 토큰을 발급하지 않아야 한다.

**검증 기준**

- 정상적인 Authorization Code와 PKCE 값으로 토큰 교환에 성공한다.
- 재사용된 Code, 잘못된 PKCE 값, 만료된 Code는 거부된다.

**관련 Use Case:** UC-01

#### FR-006. ID Token 및 Access Token 발급

**설명**

CILS는 OIDC 인증 결과를 전달하기 위한 ID Token과 API 접근에 사용할 Access Token을 발급해야 한다.

**상세 요구사항**

- FR-006-01: OIDC 인증 요청에 대해 ID Token을 발급해야 한다.
- FR-006-02: ID Token은 JWT 형식으로 발급해야 한다.
- FR-006-03: ID Token에는 `iss`, `sub`, `aud`, `exp` 등 OIDC에서 요구하는 Claim을 포함해야 한다.
- FR-006-04: CILS는 Access Token을 발급해야 한다.
- FR-006-05: 토큰에는 유효기간을 적용해야 한다.
- FR-006-06: 서명된 JWT를 사용하는 경우 클라이언트가 서명을 검증할 수 있도록 공개키 정보를 제공해야 한다.

**검증 기준**

- 정상적인 OIDC 인증 요청에 대해 ID Token과 Access Token이 발급된다.
- ID Token의 서명, 발급자, 수신 대상 및 만료 정보를 검증할 수 있다.
- 만료된 토큰은 유효한 토큰으로 인정되지 않는다.

**관련 Use Case:** UC-01

### 3.3 중앙 SSO 세션 관리

#### FR-007. 중앙 SSO 세션 생성 및 유지

**설명**

CILS는 사용자 인증에 성공한 경우 중앙 SSO 세션을 생성하고 유지해야 한다.

**상세 요구사항**

- FR-007-01: 사용자 인증에 성공하면 중앙 SSO 세션을 생성해야 한다.
- FR-007-02: 중앙 SSO 세션은 Redis를 이용하여 관리한다.
- FR-007-03: CILS는 세션을 식별할 수 있는 쿠키를 브라우저에 제공해야 한다.
- FR-007-04: 세션에는 유효기간을 적용해야 한다.
- FR-007-05: 여러 CILS 인스턴스가 동일한 중앙 세션 정보를 사용할 수 있어야 한다.

**검증 기준**

- 로그인 성공 후 중앙 SSO 세션이 생성된다.
- 서로 다른 CILS 인스턴스에서 동일한 유효 세션을 확인할 수 있다.
- 세션 만료 후 재인증을 요구한다.

**관련 Use Case:** UC-01, UC-02

#### FR-008. 애플리케이션 간 SSO 제공

**설명**

CILS는 이미 인증된 사용자가 다른 연동 애플리케이션에 접근할 때 기존 SSO 세션을 활용할 수 있도록 해야 한다.

**상세 요구사항**

- FR-008-01: 기존 SSO 세션이 유효하면 ID/PW 재입력을 생략해야 한다. 단, 재인증 정책이 적용되는 경우는 예외로 한다.
- FR-008-02: 새로운 애플리케이션에 접근할 때 해당 애플리케이션의 Role 접근 정책을 검증해야 한다.
- FR-008-03: 접근이 허용된 경우 해당 클라이언트에 대한 새로운 Authorization Code를 발급해야 한다.
- FR-008-04: 서로 다른 애플리케이션의 인증 요청 및 토큰은 각각 구분하여 처리해야 한다.

**검증 기준**

- 학생포털 로그인 후 기존 SSO 세션을 재사용할 수 있다.
- ADMIN은 기존 SSO 세션을 이용하여 다른 포털에도 로그인할 수 있다.
- STUDENT가 교수포털에 접근하면 기존 SSO 세션이 있어도 접근이 거부된다.

**관련 Use Case:** UC-01

### 3.4 로그아웃 및 세션 무효화

#### FR-009. 중앙 로그아웃

**설명**

CILS는 중앙 SSO 로그인 상태를 종료할 수 있어야 한다.

**상세 요구사항**

- FR-009-01: CILS는 중앙 로그아웃 기능을 제공해야 한다.
- FR-009-02: 로그아웃 요청 시 중앙 SSO 세션을 무효화해야 한다.
- FR-009-03: 무효화된 중앙 SSO 세션은 재사용할 수 없어야 한다.
- FR-009-04: 중앙 로그아웃 후 새로운 인증 요청에서 재인증이 필요하도록 처리해야 한다.

**검증 기준**

- 중앙 로그아웃 후 기존 SSO 세션이 무효화된다.
- 로그아웃한 사용자가 다른 애플리케이션의 신규 인증 요청을 시작하면 재인증이 요구된다.

**관련 Use Case:** UC-02

#### FR-010. 토큰 및 연동 애플리케이션 로그아웃 정책

**설명**

CILS는 로그아웃 시 토큰과 연동 애플리케이션의 인증 상태를 처리하기 위한 정책을 제공해야 한다.

**상세 요구사항 — 정책 확정 필요**

- FR-010-01: 로그아웃 시 Refresh Token 폐기 여부와 범위를 정의해야 한다.
- FR-010-02: 이미 발급된 Access Token의 유효성 처리 정책을 정의해야 한다.
- FR-010-03: 연동 애플리케이션의 로컬 로그인 세션을 종료하는 방법과 범위를 정의해야 한다.
- FR-010-04: 채택한 로그아웃 정책에 따라 필요한 무효화 및 통지 기능을 구현해야 한다.

**검증 기준**

- 결정된 로그아웃 정책에 따라 중앙 세션과 토큰의 무효화 결과를 검증한다.
- 연동 애플리케이션 세션 종료를 지원하기로 결정한 경우 관련 로그아웃 연동을 검증한다.

**관련 Use Case:** UC-02

### 3.5 Role 기반 애플리케이션 접근 인가

#### FR-011. 사용자 Role 관리

**설명**

CILS는 각 사용자 계정에 Role을 부여하고 관리해야 한다.

**상세 요구사항**

- FR-011-01: CILS는 `STUDENT`, `PROFESSOR`, `STAFF`, `ADMIN` Role을 지원해야 한다.
- FR-011-02: CILS는 사용자 계정에 부여된 Role을 조회할 수 있어야 한다.
- FR-011-03: 관리자는 사용자 Role을 변경할 수 있어야 한다.
- FR-011-04: Role 변경은 권한이 있는 관리자만 수행할 수 있어야 한다.
- FR-011-05: Role 변경에 대한 이력을 기록해야 한다.

**검증 기준**

- 각 사용자의 Role을 정상적으로 조회할 수 있다.
- 관리자만 사용자 Role을 변경할 수 있다.
- Role 변경 내역을 확인할 수 있다.

**관련 Use Case:** UC-03

#### FR-012. Role 기반 애플리케이션 접근 인가

**설명**

CILS는 사용자 Role과 애플리케이션 접근 정책을 비교하여 로그인 허용 여부를 결정해야 한다.

**상세 요구사항**

- FR-012-01: CILS는 인증된 사용자의 Role을 조회해야 한다.
- FR-012-02: OIDC Client 등록 정보를 통해 요청 대상 애플리케이션을 식별해야 한다.
- FR-012-03: Role별 접근 정책을 확인해야 한다.
- FR-012-04: 접근이 허용된 경우 Authorization Code를 발급할 수 있어야 한다.
- FR-012-05: 접근이 거부된 경우 Authorization Code를 발급하지 않아야 한다.
- FR-012-06: 명시적으로 허용되지 않은 접근은 거부해야 한다(Default Deny).
- FR-012-07: `ADMIN` Role은 모든 등록된 연동 애플리케이션에 접근할 수 있어야 한다.

**검증 기준**

- STUDENT는 STUDENT_PORTAL에 접근가능하지만 나머지는 접근 불가능하다.
- ADMIN은 세 포털 모두에 접근할 수 있다.

**관련 Use Case:** UC-01, UC-03

#### FR-013. Role별 애플리케이션 접근 정책 관리

**설명**

CILS는 관리자가 Role별 애플리케이션 접근 정책을 조회하고 변경할 수 있는 기능을 제공해야 한다.

**상세 요구사항**

- FR-013-01: 관리자는 등록된 Role과 애플리케이션별 접근 정책을 조회할 수 있어야 한다.
- FR-013-02: 관리자는 Role별 애플리케이션 접근 허용 여부를 변경할 수 있어야 한다.
- FR-013-03: 정책 변경은 권한이 있는 관리자만 수행할 수 있어야 한다.
- FR-013-04: 정책 변경 이력을 기록해야 한다.
- FR-013-05: 변경된 정책은 이후의 신규 인가 요청에 반영되어야 한다.

**검증 기준**

- 관리자가 정책을 변경할 수 있다.
- 일반 사용자는 정책을 변경할 수 없다.
- 정책 변경 후 신규 인증 요청에 변경 내용이 반영된다.

**관련 Use Case:** UC-03

#### FR-014. Role 및 접근 정책 변경 반영

**설명**

CILS는 사용자 Role 또는 Role별 접근 정책이 변경되었을 때 변경된 접근 자격을 반영할 수 있어야 한다.

**상세 요구사항 — 기존 세션·토큰 처리 정책 확정 필요**

- FR-014-01: CILS는 신규 인가 요청 시 최신 Role 및 접근 정책을 적용해야 한다.
- FR-014-02: Role 변경 후 기존 중앙 SSO 세션에 대한 처리 방식을 정의해야 한다.
- FR-014-03: 기존에 발급된 Access Token과 Refresh Token의 처리 방식을 정의해야 한다.
- FR-014-04: 이미 로그인된 연동 애플리케이션의 로컬 세션에 변경 사항을 반영하는 방식을 정의해야 한다.
- FR-014-05: 확정된 변경 반영 정책에 따라 필요한 무효화 또는 재검증 기능을 제공해야 한다.

**검증 기준**

- 변경 후 신규 인가 요청에는 최신 Role 정책이 적용된다.
- 기존 세션과 토큰에 대해서는 확정된 변경 반영 정책에 따른 동작을 검증한다.

**관련 Use Case:** UC-03, UC-01

### 3.6 연동 애플리케이션 관리

#### FR-015. OIDC Client 등록 정보 관리

**설명**

CILS는 연동 애플리케이션의 OIDC Client 등록 정보를 관리할 수 있어야 한다.

**상세 요구사항**

- FR-015-01: CILS는 연동 애플리케이션의 Client ID를 관리해야 한다.
- FR-015-02: 각 클라이언트의 Redirect URI를 관리해야 한다.
- FR-015-03: 각 클라이언트의 허용 Grant Type과 Scope를 관리해야 한다.
- FR-015-04: 클라이언트 인증 방식 및 PKCE 설정을 관리해야 한다.
- FR-015-05: 클라이언트와 서비스 코드를 연결하여 관리해야 한다.
- FR-015-06: 등록되지 않은 클라이언트의 인증 요청은 거부해야 한다.

**검증 기준**

- 등록된 클라이언트의 유효한 인증 요청을 처리할 수 있다.
- 미등록 클라이언트는 인증 요청이 거부된다.
- 클라이언트 설정 변경 후 신규 인증 요청에 변경된 설정이 반영된다.

**관련 Use Case:** UC-01, UC-03(관리 범위 확장 시)
