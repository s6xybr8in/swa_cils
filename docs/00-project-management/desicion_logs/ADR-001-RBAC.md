# ADR-001: Role 기반 애플리케이션 접근 제어 채택

| 항목 | 내용 |
|---|---|
| **ADR ID** | ADR-001 |
| **제목** | Role 기반 애플리케이션 접근 제어 채택 |
| **상태(Status)** | Accepted |
| **결정일** | 2026-11-06 |
| **프로젝트** | CILS (중앙 통합 로그인 시스템) |
| **관련 요구사항** | 사용자 인증, Role 기반 애플리케이션 접근 인가 |

## 1. 배경 (Context)

CILS는 여러 애플리케이션의 사용자 인증 및 접근 권한을 중앙에서 관리하는 통합 로그인 시스템이다.

사용자는 학생, 교수, 교직원, 관리자 등 서로 다른 역할을 가지며, 각 역할에 따라 접근할 수 있는 애플리케이션이 달라야 한다.

사용자별로 개별 접근 권한을 부여하는 방식은 사용자 수와 연동 애플리케이션이 증가함에 따라 권한 관리가 복잡해질 수 있다.

따라서 역할별로 일관된 접근 정책을 적용하면서, 중앙 인증 시스템과 개별 애플리케이션 사이의 책임을 명확히 구분할 필요가 있다.

## 2. 결정 (Decision)

CILS의 애플리케이션 접근 인가 방식으로 **RBAC(Role-Based Access Control, 역할 기반 접근 제어)** 를 채택한다.

### 2.1 사용자 Role 정의

사용자 역할은 다음 네 가지로 구분한다.

| Role | 설명 |
|---|---|
| `STUDENT` | 학생 |
| `PROFESSOR` | 교수 |
| `STAFF` | 교직원 |
| `ADMIN` | 관리자 |

### 2.2 Role별 애플리케이션 접근 정책

현재 프로젝트 개발 용이성을 위해서 이렇게 간소화해서 진행한다.

| 애플리케이션 | STUDENT | PROFESSOR | STAFF | ADMIN |
|---|:---:|:---:|:---:|:---:|
| 학생포털 (`STUDENT_PORTAL`) | O | X | X | O |
| 교수포털 (`PROFESSOR_PORTAL`) | X | O | X | O |
| 교직원포털 (`STAFF_PORTAL`) | X | X | O | O |

※ O: 접근 허용 / X: 접근 거부

관리자(`ADMIN`)는 모든 등록된 연동 애플리케이션에 접근할 수 있도록 한다.


### 2.3 접근 인가 절차

1. 사용자가 연동 애플리케이션에 로그인을 요청한다.
2. CILS가 사용자의 인증 상태를 확인한다.
3. CILS가 사용자의 Role을 조회한다.
4. 요청한 애플리케이션과 Role별 접근 정책을 비교한다.
5. 접근이 허용되면 Authorization Code를 발급한다.
6. 접근이 거부되면 해당 애플리케이션에 대한 인증·인가 요청을 거부한다.

### 2.4 권한 관리 원칙

- 사용자별 개별 접근 권한 대신 Role 기반 접근 정책을 적용한다.
- 하나의 Role에 여러 애플리케이션의 접근 권한을 부여할 수 있다.
- `ADMIN`은 모든 등록된 연동 애플리케이션에 접근할 수 있다.
- 명시적으로 허용되지 않은 애플리케이션 접근은 거부한다(Default Deny).
- 사용자 Role과 Role별 애플리케이션 접근 정책은 CILS에서 중앙 관리한다.
- 애플리케이션 내부의 세부 기능 및 데이터 접근 권한은 각 애플리케이션이 독립적으로 관리한다.

## 3. 결정 근거 (Rationale)

### 3.1 권한 관리 단순화

사용자마다 접근 권한을 개별적으로 설정하는 대신 Role을 기준으로 관리하여 권한 정책의 복잡성을 줄인다.

### 3.2 일관된 접근 정책

동일한 Role을 가진 사용자에게 동일한 애플리케이션 접근 정책을 적용하여 중앙에서 일관된 인가 판단을 수행한다.

### 3.3 책임의 명확한 분리

CILS는 애플리케이션 접근 가능 여부만 판단하고, 애플리케이션 내부의 세부 권한 관리는 각 애플리케이션에 위임한다.

이를 통해 중앙 인증 시스템과 개별 애플리케이션 사이의 책임을 명확히 구분한다.

### 3.4 확장성

새로운 연동 애플리케이션을 추가할 경우, 기존 사용자별 권한을 수정하는 대신 Role별 접근 정책을 정의하여 확장할 수 있다.

## 4. 고려한 대안 (Alternatives Considered)

### 4.1 사용자별 개별 권한 관리
